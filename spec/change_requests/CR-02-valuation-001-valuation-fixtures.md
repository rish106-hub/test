# CR-02-valuation-001: promote the 02-valuation synthetic fixtures to tests/fixtures/synthetic

Requested by: 02-valuation            Date: 2026-10-25
Contract section: test_plan §W (W-03), workbook_interface §1 (stubbed builds), D-013, D-030

## Problem

`tests/fixtures/synthetic/` has no `raw_financials.csv`, `corporate_actions.csv` or `assumptions.csv`. The synthetic registry puts S90001 (entity E9001) on VAL_HDFC_BANK, but nothing gives it a balance sheet, dividends or drivers, so a test build would value it from empty tables.

02-valuation works around this on its own paths:

* The fixtures live in `tests/valuations/fixtures/synthetic/` and come from `tests/valuations/make_valuation_fixtures.py` (`--check` mode, tested in `tests/valuations/test_valuation_module.py`).
* `src/valuations/fixtures.py` appends them to ModelData **only** in an isolated test build (`--only 02-valuation`, detected because `tbl_Registry` is not built yet). The stubs of `tbl_RawFinancials` and `tbl_CorporateActions` are made after the module builders run, so they include the rows.

The workaround cannot help the **integrated** test build. There, 01-data builds `tbl_RawFinancials` before 02-valuation runs, so S90001's VAL sheet links Observation_IDs that the table does not hold. Its inputs show MISSING and its row is UNVALUED. The Python reference must then skip the fixtures too, so the reference and the workbook stay consistent; that part already works. W-03 on the integrated test build would have no valued security to compare.

## Proposal

1. Move the three CSVs into `tests/fixtures/synthetic/` (same rows and IDs), generated by `tools/make_synthetic_fixtures.py`. The cleanest way is to import `tests/valuations/make_valuation_fixtures.py` and call its three row functions (`raw_financials()`, `corporate_actions()`, `assumptions()`). That keeps one generator, and its `--check` keeps both in sync.
2. Add four GLOBAL weight rows to the promoted `assumptions.csv`, as synthetic copies of `data/canonical/assumptions.csv`. Once a fixture file exists, `build/data_loader.py` reads it **instead of** the canonical file in a test build, so the D-009 weights would otherwise disappear. Use these values: `W_RI` 1, `W_DDM` 0, `W_JPB` 0, `W_PEER_PB` 0, Source_ID `SRC-SYNTH-VAL-0001`, status `SYNTHETIC TEST FIXTURE`.
3. Nothing else changes. `augment_test_fixtures` skips rows whose primary key is already present, so it becomes a no-op, and 02-valuation deletes it after the merge.

## Impact on other workers

* 01-data: none. A production build never reads the fixtures (D-013), and every row is `SYNTHETIC TEST FIXTURE` with an `SRC-SYNTH-*` Source_ID.
* 03-nav: none. 03-nav reads `tbl_ValuationOutputs`, and its isolated build still uses the stubbed `valuation_outputs.csv` fixture.
* 05-qa: the integrated test build gains a fully valued S90001 for W-03.

## Tests

No contract definition changes. Existing evidence on branch `wave1/02-valuation`:

* `tests/valuations/test_valuation_module.py::test_fixtures_are_in_sync_with_their_generator`
* `tests/valuations/test_sheet_matches_reference.py` (15 tests). It recalculates the isolated build and compares every `out_*` name and intermediate cell with the reference, to 1e-9.

After promotion, one more check: in the integrated test build, `out_S90001_FV_Base` should equal `reference_valuation_outputs.csv`. In the isolated build it reads 712.554505133464 today (recalculated in LibreOffice); the integrated build should read the same once the fixtures are promoted.
